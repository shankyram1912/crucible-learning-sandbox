# Hello World Spec: Day-0 Bootstrap

> Parent: [helloworld-spec.md](helloworld-spec.md)

Day-0 bootstrap creates the **Control Tower** foundation that everything else runs on. It is run **once, by a human org admin**, one operation at a time. This spec covers the execution model, configuration, the `run.sh` runner, progress tracking, and the baseline steps.

---

## 1. Execution model

1. The **org admin** signs in to the Google Cloud console for the org and opens **Cloud Shell**.
2. The admin **clones the repo manually** (`git clone ...`). Cloning is not automated.
3. The admin fills in **`initialize.env`** (one file holding every setting).
4. The admin runs each operation with **`./run.sh --operation=<OperationName>`**, one operation at a time, in order.

**Why Cloud Shell:** gcloud and git are preinstalled (and usually Terraform; if not, the optional `install-terraform.sh` installs it, see section 2.1); Terraform runs as the signed-in admin with no key files; the home directory persists between sessions. Nothing in GCP can run Day-0 itself, because Day-0 is what creates the platform.

---

## 2. Layout

```
helloworld/src/terraform/control-tower/
├── README.md                 admin runbook (how to run)
├── initialize.env.example    committed template
├── initialize.env            settings + generated outputs (gitignored)
├── initialize.sh             loads and validates settings (sourced)
├── run.sh                    operation runner
├── install-terraform.sh      optional standalone Terraform installer
├── controltower.status       progress per operation (gitignored, generated)
├── logs/                     run logs (gitignored, generated)
├── 01-control-tower-project-create/
│   ├── operation.md          long description printed before the run
│   └── *.tf                  Terraform root
└── 02-control-tower-apis-enable/
    ├── operation.md
    └── *.tf
```

Each operation folder is its **own Terraform root** with its **own `terraform init` and state**, plus an `operation.md` describing it. The numeric prefix only fixes the order.

### 2.1 Optional Terraform installer (`install-terraform.sh`)
- Standalone, no sudo: installs Terraform (default `1.17.1`, or `--version=<x.y.z|latest>`) into `~/.local/bin` (persists in Cloud Shell's home), or `--dir=<path>`.
- Verifies the download against HashiCorp's published SHA256 checksums; detects `amd64` / `arm64`.
- Adds the install directory to `PATH` in `~/.bashrc` unless `--no-profile`.
- Idempotent: skips the download if the requested version is already installed.
- Not called by `run.sh`; validation points to it when `terraform` is missing or too old.

## 3. Configuration

### 3.1 `initialize.env` holds everything
One file holds the quota project, every Terraform input, and the outputs written back by operations. Plain `KEY=value` lines, in two sections. Because `initialize.sh` sources the file, a value can be derived from an earlier key (for example `CT_PROJECT_ID=lsb-control-tower-${ORG_SUFFIX}`).

```
# ---- admin settings ----
QUOTA_PROJECT=...
...
# ---- generated by run.sh (do not edit) ----
CT_FOLDER_ID=...
CT_PROJECT_NUMBER=...
```

Every key is also exported to Terraform as a lowercase `TF_VAR_` copy (for example `ORG_ID` becomes `TF_VAR_org_id`).

#### Admin settings

**Session and quota**
| Key | What it is | Example | Notes |
|---|---|---|---|
| `QUOTA_PROJECT` | Project that gcloud and Terraform API calls are **billed and rate-limited against**. Not where resources are created. | `some-existing-project` | Needed because the Control Tower project does not exist yet when `ControlTowerProjectCreate` runs. Must have Resource Manager, Service Usage, Cloud Billing and Cloud Storage APIs enabled. After the first operation the admin can switch it to `CT_PROJECT_ID`. |

**Organization and identity**
| Key | What it is | Example | Notes |
|---|---|---|---|
| `ORG_ID` | Numeric ID of the GCP organization | `69296271958` | Org-level lookups and the default folder parent |
| `DIRECTORY_CUSTOMER_ID` | Workspace / Cloud Identity customer ID | `C03ccny1h` | Required to create Google Groups later (`parent=customers/<id>`). Not used by the first two operations. |
| `DOMAIN` | Primary domain of the org | `shankyram.altostrat.com` | Email validation and group naming later. Not used by the first two operations. |

**Billing**
| Key | What it is | Example | Notes |
|---|---|---|---|
| `BILLING_ACCOUNT_ID` | Billing account linked to the Control Tower project | `XXXXXX-XXXXXX-XXXXXX` | The admin needs Billing User on it. Without billing most APIs cannot be enabled. |

**Control Tower folder**
| Key | What it is | Example | Notes |
|---|---|---|---|
| `CT_FOLDER_NAME` | Display name of the folder that holds the Control Tower project | `Control Tower` | Only used when the folder is created |
| `CT_FOLDER_PARENT` | Where the folder is created: the org or another folder | `organizations/69296271958` or `folders/361218745460` | Decides whether the Control Tower sits beside the playground root or inside it |
| `CT_FOLDER_ID` | Numeric ID of an existing folder to use | empty, or `123456789012` | **Empty = create** `CT_FOLDER_NAME` under `CT_FOLDER_PARENT`. **Set = use that folder** and skip creation. Written back automatically after creation, so re-runs reuse it. |

**Control Tower project**
| Key | What it is | Example | Notes |
|---|---|---|---|
| `CT_PROJECT_ID` | Globally unique ID of the Control Tower project | `lsb-control-tower-${ORG_SUFFIX}` (e.g. `lsb-control-tower-e26`) | Hosts the Self Service APIs, Firestore, the state bucket and later Cloud Run. Project IDs are unique across **all of Google Cloud** and never reusable after deletion, so the default adds `ORG_SUFFIX` (first 3 hex characters of a SHA-256 hash of `ORG_ID`, computed by `initialize.sh`): deterministic per org, 4,096 possible values, which makes a clash unlikely but not impossible (check in the Console New Project dialog). Cannot be changed once created. Availability can be checked in the Console New Project dialog (validation cannot detect IDs owned outside the org). |
| `REGION` | Default region for regional resources | `asia-southeast1` | State bucket, Firestore, Artifact Registry, Cloud Run. Should match the allowed-locations org policy later. |

**Platform resources**
| Key | What it is | Example | Notes |
|---|---|---|---|
| `TF_STATE_BUCKET` | Bucket for all Terraform state and runner backups | `${CT_PROJECT_ID}-bucket` (e.g. `lsb-control-tower-e26-bucket`) | Created by `ControlTowerProjectCreate`. Bucket names are global, so it is derived from the project ID. Also holds the `initialize.env`, status and log backups used by `Restore`. |
| `FIRESTORE_DATABASE` | ID of the Firestore database used by the Self Service APIs | `lsb-control-tower-db` | Created by a later operation. 4 to 63 characters: lowercase letters, digits, hyphens. |

#### Generated section (written by `run.sh`, do not edit)
| Key | Written by | What it is | Used for |
|---|---|---|---|
| `CT_FOLDER_ID` | `ControlTowerProjectCreate` (when it creates the folder) | ID of the created folder | Re-runs reuse it; later operations reference it |
| `CT_FOLDER_MANAGED` | `ControlTowerProjectCreate` | `true` when this operation created the folder and keeps managing it | Keeps Terraform from planning to remove the folder once `CT_FOLDER_ID` is filled in |
| `CT_PROJECT_NUMBER` | `ControlTowerProjectCreate` | Numeric project number (different from the project ID) | Later IAM operations, which need service agent emails such as `service-<number>@gcp-sa-...` |

#### Minimum keys for the first two operations
`ControlTowerProjectCreate` and `ControlTowerApisEnable` only need `QUOTA_PROJECT`, `ORG_ID`, `BILLING_ACCOUNT_ID`, `CT_FOLDER_NAME`, `CT_FOLDER_PARENT`, `CT_FOLDER_ID`, `CT_PROJECT_ID`, `REGION` and `TF_STATE_BUCKET`. The other keys can stay as placeholders until their operations exist; validation only requires the keys used by the operation being run.

### 3.2 Outputs are written back to `initialize.env`
- At the end of a successful operation, `run.sh` reads `terraform output` and **updates the matching keys in the generated section** of `initialize.env` (added if missing, replaced if present).
- Example: `ControlTowerProjectCreate` creates the folder, then writes `CT_FOLDER_ID`. On a re-run, the folder ID is set, so the existing folder is used instead of creating another.
- A copy of `initialize.env` is saved to the state bucket after each operation, so it can be recovered in a fresh Cloud Shell.

### 3.3 `initialize.sh`
1. **Must be sourced** (`source ./initialize.sh`), never executed. If executed, it stops and prints the correct command.
2. Computes `ORG_SUFFIX` (first 3 hex characters of `sha256(ORG_ID)`), then loads `initialize.env`, so keys can use `${ORG_SUFFIX}`. A value set in the file overrides the computed one.
3. **Validates** that every required key is set and non-empty, and lists all missing keys at once.
4. Exports every key as-is, plus a lowercase **`TF_VAR_`** copy (for example `BILLING_ACCOUNT_ID` becomes `TF_VAR_billing_account_id`), using a generic loop. Adding a setting is one new line in `initialize.env`, with no script change.
5. Sets the quota project for both tools, for this session only (global gcloud config is not changed): `CLOUDSDK_CORE_PROJECT` + `CLOUDSDK_BILLING_QUOTA_PROJECT` for gcloud, and `GOOGLE_BILLING_PROJECT` + `USER_PROJECT_OVERRIDE=true` for Terraform.
6. Sets `TF_INPUT=0` so Terraform fails instead of prompting for a missing variable.
7. Sets `TF_CLI_ARGS_init="-backend-config=bucket=$TF_STATE_BUCKET"` so every `terraform init` uses the state bucket. Each operation's backend block hardcodes only its own prefix (for example `control-tower/02-control-tower-apis-enable`).
8. Prints a short summary of what was loaded and adds a prompt prefix such as `[ct: lsb-control-tower-e26]`.

#### Variables set automatically by `initialize.sh` (not in the file)
| Variable | Purpose |
|---|---|
| `ORG_SUFFIX` | First 3 hex characters of `sha256(ORG_ID)`, used to make global names unique (for example `e26`) |
| `TF_VAR_*` | Lowercase copies of every key, read by Terraform |
| `CLOUDSDK_CORE_PROJECT` + `CLOUDSDK_BILLING_QUOTA_PROJECT` | Make gcloud use `QUOTA_PROJECT` for this session only |
| `GOOGLE_BILLING_PROJECT` + `USER_PROJECT_OVERRIDE=true` | Make Terraform bill API calls to `QUOTA_PROJECT` |
| `TF_INPUT=0` | Terraform fails instead of prompting for a missing value |
| `TF_CLI_ARGS_init` | Passes `-backend-config=bucket=$TF_STATE_BUCKET` to every `terraform init` |

### 3.4 The shell never has to hold config
`run.sh` **sources `initialize.sh` itself on every run**, so config always comes from the file, not from whatever the shell happens to hold. New Cloud Shell tabs, reconnects and timeouts do not matter. Manual `source ./initialize.sh` is only for ad-hoc `terraform` or `gcloud` commands.

## 4. `run.sh`

Usage: `./run.sh --operation=<OperationName> [--validate-only] [--describe] [--yes] [--force] [--no-tmux]`

### 4.1 Operations
| Operation | Kind | Does |
|---|---|---|
| `Status` | utility | Table of all operations: status, time, who ran it, git commit |
| `Restore` | utility | In a fresh Cloud Shell, pulls `initialize.env`, `controltower.status` and logs back from the state bucket |
| `ControlTowerProjectCreate` | bootstrap (order 1) | Control Tower folder (or existing), project, billing link, state bucket |
| `ControlTowerApisEnable` | bootstrap (order 2) | Enables the baseline APIs on the Control Tower project |

New bootstrap operations are added as new numbered folders with a PascalCase operation name.

### 4.2 Long description before every bootstrap operation
Before anything runs, `run.sh` prints the operation's **`operation.md`** in full, filled in with the actual values from `initialize.env`. Every `operation.md` has the same sections:

| Section | Content |
|---|---|
| **Summary** | One paragraph: what this operation does and why |
| **Prerequisites** | Operations that must be `DONE`, and permissions the admin needs |
| **Inputs** | The `initialize.env` keys used, with their current values |
| **What will happen** | Numbered list of every action, in order (create, link, enable, migrate) |
| **Resources created or changed** | Each GCP resource, with name and location |
| **Written back** | Keys written to `initialize.env` on success |
| **Readiness check** | What is verified before the operation is marked `DONE` |
| **Expected duration** | Rough time |
| **Re-run behavior** | What happens if run again (idempotent, skips existing) |
| **Cannot be undone** | Anything irreversible or protected (for example `prevent_destroy`) |

`--describe` prints the long description only and exits, without running anything.

Example (abridged):
```
$ ./run.sh --operation=ControlTowerProjectCreate

 ControlTowerProjectCreate                                       order 1 of 2

 Summary
   Creates the Control Tower project that hosts the Self Service APIs, Firestore
   and all Terraform state, inside the Control Tower folder.

 Inputs (initialize.env)
   ORG_ID              69296271958
   CT_FOLDER_ID        (empty)  -> folder "Control Tower" will be created
   CT_FOLDER_PARENT    folders/600433119916
   CT_PROJECT_ID       lsb-control-tower-e26
   BILLING_ACCOUNT_ID  XXXXXX-XXXXXX-XXXXXX
   REGION              asia-southeast1
   TF_STATE_BUCKET     lsb-control-tower-e26-bucket

 What will happen
   1. Create folder "Control Tower" under folders/600433119916 (University Sandbox)
   2. Create project lsb-control-tower-e26 in that folder
   3. Link billing account XXXXXX-XXXXXX-XXXXXX
   4. Create bucket gs://lsb-control-tower-e26-bucket (asia-southeast1, versioned)
   5. Move this operation's Terraform state into the bucket
   6. Wait until the project is ACTIVE and billing is enabled
   7. Write CT_FOLDER_ID and CT_PROJECT_NUMBER back to initialize.env

 Expected duration  ~2 minutes
 Re-run             safe; existing folder/project/bucket are kept
 Cannot be undone   project and bucket are protected from deletion

 Terraform plan: 4 to add, 0 to change, 0 to destroy
 Proceed? [y/N]
```

### 4.3 What a bootstrap operation does, in one go
1. Loads config (`initialize.sh`) and validates the operation (section 4.4). Any problem stops the run before anything changes.
2. Prints the long description (section 4.2).
3. Checks the previous operation is `DONE`.
4. Marks the operation `RUNNING`.
5. `terraform init`, then `terraform plan -out=tfplan` and shows the plan summary.
6. Asks for confirmation (skipped with `--yes`).
7. `terraform apply tfplan`, applying exactly what was shown.
8. Runs the readiness check.
9. Writes outputs back to `initialize.env`.
10. Marks the operation `DONE` (or `FAILED` on any error).

- `--validate-only` runs the operation's validation and stops; `--describe` only prints the description; `--yes` skips the confirmation prompt; `--force` runs an operation even if the previous one is not `DONE`; `--no-tmux` runs in the current shell instead of the tmux session.
- **tmux is built in:** in an interactive terminal, a bootstrap operation relaunches itself inside the tmux session `lsb-day0` (reattach with `tmux attach -t lsb-day0`). It is skipped for `Status`, `Restore`, `--describe`, `--validate-only`, `--no-tmux`, non-interactive runs, or when already inside tmux. If the session already exists, `run.sh` refuses to start a second run.
- There is **no destroy operation**.

### 4.4 Validation is built into every operation
Validation is not a separate operation. Every bootstrap operation validates itself first, and `--validate-only` runs just that part. It has three layers:

| Layer | Checks | Applies to |
|---|---|---|
| **Shared** | Required tools and versions (terraform, gcloud, jq, envsubst, git); active gcloud account; quota project reachable | Every operation |
| **Registry** | The `initialize.env` keys the operation declares; the APIs it declares as required on the quota project | Each operation, from its registry entry in `run.sh` |
| **Operation hook** | `validate_<OperationName>` function for checks specific to that operation (for example billing account visible, folder parent accessible, project ID already taken) | Operations that define a hook |

- All problems are listed at once, and nothing changes if any problem is found.
- Hooks can also raise **warnings** (shown, but not blocking), for example "project already exists".
- Adding an operation means adding its registry entry (keys, quota APIs) and, if needed, its `validate_<OperationName>` hook. No change to the validation code itself.

## 5. Progress status tracking

### 5.1 Where status lives
Status is kept in **`controltower.status`**, separate from `initialize.env` because it records what happened (a run log), not configuration. Sourceable `KEY=value` lines per operation:
```
ControlTowerProjectCreate_STATUS=DONE
ControlTowerProjectCreate_AT=2026-11-08T12:30Z
ControlTowerProjectCreate_BY=admin@shankyram.altostrat.com
ControlTowerProjectCreate_COMMIT=67f86fe
ControlTowerApisEnable_STATUS=FAILED
ControlTowerApisEnable_AT=2026-11-08T12:41Z
ControlTowerApisEnable_ERROR="firestore.googleapis.com: billing not ready"
```

### 5.2 How it is updated
| Moment | Written by `run.sh` |
|---|---|
| Operation starts | `STATUS=RUNNING`, `AT`, `BY` (gcloud account), `COMMIT` (git commit of the clone) |
| Apply and readiness succeed | `STATUS=DONE`, `AT` |
| Any command fails, or the script is interrupted | A shell `trap` sets `STATUS=FAILED`, `AT`, `ERROR` (last error line) |
| After every update | The file is copied to the state bucket (from `ControlTowerProjectCreate` onward) |

### 5.3 Rules
1. States: `NOT_STARTED` (no entry yet), `RUNNING`, `DONE`, `FAILED`.
2. **Order is enforced:** an operation only runs when the previous one (by order) is `DONE` (unless `--force`).
3. An operation left `RUNNING` (for example Cloud Shell closed mid-apply) is shown as **interrupted** by `Status`; re-running it is safe because Terraform picks up from its state.
4. **Shared through the state bucket**, so a new Cloud Shell or a second admin sees the same progress (`restore`).
5. Re-running a `DONE` operation is safe: Terraform shows no changes, which also re-verifies it.

### 5.4 Status output
```
 Control Tower Day-0                         project lsb-control-tower-e26

  ✔ 1  ControlTowerProjectCreate   DONE         2026-11-08 12:30  admin@  67f86fe
  ✖ 2  ControlTowerApisEnable      FAILED       2026-11-08 12:41  billing not ready
```
Colors follow [apiservices-spec.md](apiservices-spec.md) section 5.1.

## 6. Best practices

1. **Validate before every operation** (built in, section 4.4): shared, registry and operation-specific checks; all problems listed at once; nothing changes on failure.
2. **Apply exactly what was planned:** the plan is saved, shown, confirmed, then applied as-is.
3. **Pin versions:** `required_version`, pinned providers, and committed `.terraform.lock.hcl`.
4. **Log every run** to `logs/<OperationName>-<timestamp>.log` in Cloud Shell (never in the repo), and copy logs to the state bucket.
5. **tmux built in** (section 4.3): interactive runs use the `lsb-day0` tmux session so a Cloud Shell disconnect does not kill a running apply.
6. **Protect critical resources:** `prevent_destroy` on the project, state bucket and Firestore database, plus GCP deletion protection where available.
7. **Label everything** with `managed-by=lsb-day0` and `operation=<operation-name>`.
8. **Strict shell mode:** `set -euo pipefail` in scripts.
9. **Gitignore** `initialize.env`, `controltower.status`, `logs/`, `.terraform/`, `*.tfplan`.
10. **Idempotent operations:** every operation can be re-run safely.

## 7. Baseline operations

### 1. `ControlTowerProjectCreate` (`01-control-tower-project-create`)
1. **Folder:** if `CT_FOLDER_ID` is set, use that existing folder and skip creation; if empty, create `CT_FOLDER_NAME` under `CT_FOLDER_PARENT`.
2. **Project:** create `CT_PROJECT_ID` in the folder and link `BILLING_ACCOUNT_ID`.
3. **Cloud Storage API:** enabled on the new project (needed before the bucket can be created).
4. **State bucket:** create `TF_STATE_BUCKET` in the project (in `REGION`, versioning on, 7-day soft delete, uniform bucket-level access, public access prevented).
5. **State:** this operation starts with **local state** (no bucket exists yet). After apply, `run.sh` generates `backend.tf` (gitignored) and **migrates the state into the bucket** under `control-tower/01-control-tower-project-create`. In a fresh clone, `run.sh` detects the remote state and generates `backend.tf` before `terraform init`, so nothing is created twice.
6. **Written back to `initialize.env`:** `CT_FOLDER_ID`, `CT_FOLDER_MANAGED`, `CT_PROJECT_NUMBER`.
7. **Readiness:** project `ACTIVE` and billing enabled before `ControlTowerApisEnable` can run.

### 2. `ControlTowerApisEnable` (`02-control-tower-apis-enable`)
1. Own root and state (`control-tower/02-control-tower-apis-enable`), project ID from `initialize.env`.
2. API list is a variable; baseline:
   - Platform: `serviceusage`, `cloudresourcemanager`, `iam`, `iamcredentials`, `logging`, `monitoring`
   - Billing: `cloudbilling`, `billingbudgets`
   - Data and state: `firestore`, `storage`
   - Runtime and CI/CD: `run`, `artifactregistry`, `cloudbuild`, `secretmanager`
   - Identity: `cloudidentity`
3. APIs are **never disabled on destroy** (an enabled service is never disabled).
4. **Readiness:** every listed API `ENABLED`, and service agents exist for Cloud Run, Cloud Build and Artifact Registry.

### Later operations
To be defined one by one (service accounts and IAM, Firestore database, Artifact Registry, build and deploy pipelines, Cloud Run services, org guardrails).
