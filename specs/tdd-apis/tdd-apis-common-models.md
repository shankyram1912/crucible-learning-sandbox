# LSB Control Tower TDD: APIs, Common Models

> Parent: [tdd-apis-master.md](tdd-apis-master.md)

Models shared by every API domain, independent of any single operation. Domain specs define their own request and response bodies and reference this file for everything common. In code these are the Pydantic models in `src/api/models/common.py` (one `src/api/models/<domain>.py` per domain spec) and the request context dependency in `src/api/context.py`. The OpenAPI document (`/openapi.json`, `/docs`) is generated from the models, never hand-written. When an operation is built, its Pydantic models must match the field tables in its spec. Frozen originals: [apis-v0-interface.md](../../specs-reference/apis-v0-interface.md) A.4 and A.5.

---

## 1. Conventions
1. **Field names** are `snake_case`; **timestamps** are RFC 3339 in UTC (`2026-11-09T01:30:00Z`); **IDs** are strings; **emails** are lowercase.
2. **Requests are strict:** unknown fields are rejected with `400 INVALID_REQUEST`.
3. **Responses can grow:** new fields may be added; clients (the CLI) ignore fields they do not know.
4. **Enums** are uppercase strings.
5. **Plain resources, no envelope:** a successful response body is the resource itself. Metadata (request and session IDs) travels in HTTP headers, and success or failure is the HTTP status code. The only standard wrappers are `Page` for lists and the error object.

---

## 2. Request headers (sent by the client)

| Header | Required | Meaning |
|---|---|---|
| `Authorization: Bearer <ID token>` | yes | Google ID token (CLI) or Firebase ID token (future UI), see [tdd-apis-common-auth.md](tdd-apis-common-auth.md) |
| `X-LSB-Access-Token` | config-stage calls only | The caller's own OAuth access token, used as the user for folder, IAM and tag changes; never stored |
| `X-LSB-Session-Id` | recommended | One ID per user session, to link every request, job and log line to a session in the client. **CLI:** `LSB_SESSION_ID` if set, otherwise generated and cached for a few hours. **Future UI:** one per sign-in or browser session |
| `X-Request-Id` | no | One ID per call; generated by the API if absent |
| `User-Agent` | recommended | `lsb-cli/<version>` or `lsb-ui/<version>` |

Session and request IDs are for **correlation only, never for authorization**. Identity always comes from the verified token.

---

## 3. RequestContext (built by the API, never accepted from the client)

Built once per request by middleware from the verified token and the headers above, passed to every handler (FastAPI dependency), and written to logs, jobs and audit. A client cannot supply or override any of these fields in a request body.

| Field | Source | Description |
|---|---|---|
| `request_id` | `X-Request-Id`, or generated | Unique per call; returned in the `X-Request-Id` response header |
| `session_id` | `X-LSB-Session-Id` | Client session; absent if not sent |
| `received_at` | API clock | |
| `caller.email` | Verified token | Lowercase email; the identity used for authorization |
| `caller.subject` | Verified token (`sub`) | Permanent Google account ID. **Audit only, never used for authorization:** written to logs and jobs next to the email, so a record still identifies the right person if an account is renamed, or deleted and its email reused |
| `caller.token_type` | Verified token issuer | `GOOGLE` or `FIREBASE` |
| `client.id` | Verified token (`aud` / `azp`) | OAuth client the token was issued to, so the CLI and a future UI are told apart |
| `client.name`, `client.version` | `User-Agent` | For example `lsb-cli`, `0.1.0` |
| `personas` | Group membership (transitive), resolved on demand | `IT_ADMIN`, `BU_ADMIN`, `PLATFORM_ADMIN` (definitions below); looked up only by operations that need them |

**Personas resolved from groups** (transitive membership, so nested groups count):

| Persona | Member of | Notes |
|---|---|---|
| `IT_ADMIN` | `IT_ADMINS_GROUP` (`grp-lsb-it-admins@`) | |
| `BU_ADMIN` | `BU_ADMINS_GROUP` (`grp-lsb-bu-admins@`) | Includes every IT Admin (nested) |
| `PLATFORM_ADMIN` | **any group in `LSB_PLATFORM_ADMIN_GROUPS`** ([tdd-apis-common-config.md](tdd-apis-common-config.md)). Today: `grp-lsb-bu-admins@` | Platform-level diagnostics such as `health db`. Today this means every IT Admin and BU Admin. Support or operations staff who are neither can be added later by adding their group to the list (no code change) |

## 4. Response headers and wrappers

1. **Every response** carries `X-Request-Id`, and `X-LSB-Session-Id` if the request had one.
2. **`Accepted`** (`202`, asynchronous operations):

| Field | Type | Required | Description |
|---|---|---|---|
| `job_id` | string | yes | The job to follow (section 6) |
| `request_id` | string | yes | Same as the response header, for convenience |

3. **`Page`** (list operations):

| Field | Type | Required | Description |
|---|---|---|---|
| `items` | list | yes | Resources of the operation's type |
| `next_page_token` | string | no | Pass as `page_token` to get the next page; absent on the last page |

## 5. Error
Every error response (`4xx`, `5xx`) uses one shape. The only exception is `health db`, which returns `503` with its own health body ([tdd-apis-health.md](tdd-apis-health.md)).

```json
{
  "error": {
    "code": "PRECHECK_FAILED",
    "message": "2 problems found",
    "request_id": "r-20261109-7f3a",
    "details": [
      { "field": "owners[0]", "problem": "user not found in directory: lsb-owner-ba10@shankyram.altostrat.com" },
      { "field": "bu_subcategory", "problem": "does not match ^[a-z]([a-z0-9-]{0,61}[a-z0-9])?$" }
    ]
  }
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `error.code` | enum (below) | yes | Machine-readable code |
| `error.message` | string | yes | Short human-readable summary |
| `error.request_id` | string | yes | Same as the `X-Request-Id` header, so an error report leads straight to the logs |
| `error.details` | list of `{field, problem}` | no | Every problem found, not just the first (pre-checks and validation) |
| `error.details[].field` | string | no | Request field the problem refers to (JSON path), absent for general problems |
| `error.details[].problem` | string | yes | What is wrong |

| HTTP | `code` | When |
|---|---|---|
| `400` | `INVALID_REQUEST` | Malformed body or parameters, unknown fields |
| `401` | `UNAUTHENTICATED` | Missing, invalid or expired bearer token |
| `403` | `PERMISSION_DENIED` | Caller is authenticated but not allowed this action |
| `404` | `NOT_FOUND` | Unknown Playground Folder, playground, template, group or job |
| `409` | `JOB_IN_PROGRESS` | The target (for example the playground) already has an active job |
| `422` | `PRECHECK_FAILED` | Pre-check problems, all listed in `details` |
| `500` | `INTERNAL` | Unexpected failure (details only in the API log) |

## 6. Job
Returned as `Accepted` by every asynchronous operation and in full by the jobs domain.

| Field | Type | Required | Description |
|---|---|---|---|
| `job_id` | string | yes | For example `job-20261109-0001` |
| `type` | enum | yes | What the job does; values are defined by the domain specs (for example `CREATE_PLAYGROUND`, `SET_MEMBERS`, `ENABLE_SERVICES`) |
| `target` | `{kind, id}` | yes | What it acts on; `kind` is `PLAYGROUND_FOLDER`, `PLAYGROUND` or `GROUP` |
| `config_version` | integer | no | Config version applied, for pipeline jobs ([tdd-master.md](../tdd-master.md) section 1.9) |
| `status` | enum | yes | `QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED` |
| `requested_by` | string (email) | yes | `caller.email` of the request that started it |
| `requested_by_subject` | string | yes | `caller.subject` of that request (audit) |
| `request_id` | string | yes | Request that started it |
| `session_id` | string | no | Client session of that request |
| `client_id` | string | yes | `client.id` of that request |
| `created_at`, `updated_at` | timestamp | yes | |
| `finished_at` | timestamp | no | Set when `SUCCEEDED` or `FAILED` |
| `counts` | `{total, done, running, pending, failed}` | yes | Task counts |
| `tasks` | list of Task | yes | In execution order |

## 7. Task

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | yes | Stable within the job, for example `precheck`, `projects`, `service-gcs` |
| `label` | string | yes | Human-readable, shown by the CLI |
| `status` | enum | yes | `PENDING`, `APPLYING`, `CREATED`, `GETTING_READY`, `DONE`, `FAILED`, `SKIPPED` |
| `detail` | string | no | Current step or failure reason, for example `billing not enabled yet (attempt 3)` |
| `started_at`, `finished_at` | timestamp | no | |
